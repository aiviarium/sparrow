# Sparrow reference server (design note)

> Design note, not part of the specification. Snapshot of the live draft, revision 10, exported for this repository, with the details and deviations of the Go implementation (phases 3 and 4) added in this copy; they are marked *(implementation)* and go back to the live draft. The live document is the source of truth.

The reference server is a Go program, `sparrow-hub`, that implements the core protocol, the Hub Profile, the hub side of the Web Profile and `sparrow.hub.admin` v1. This note describes how it is built and configured. It is not part of the spec: another hub may make every choice here differently and still interoperate.

## 1. Layout

| Package | Purpose |
| --- | --- |
| `wire` | Varints, framing, every message kind, metadata, credit sizes |
| `status` | Status codes and transport close-code mapping |
| `schema` | Facets: model, canonical form, hashes, validation, compatibility, interface conformance, deltas |
| `value` | Schema-driven encoding of values |
| `websign` | Module signatures, certificates, revocation (Web Profile 9.5) |
| `session` | One Sparrow session over any binding: handshake, control messages, calls, credit, leases, schema updates |
| `transport` | Bindings: WebTransport (quic-go, webtransport-go), WebSocket *(implementation: and an in-memory binding for tests)* |
| `node` | A small library for writing nodes and clients: publish facets, serve methods, call others |
| `hub` | Composition, forwarding, call contexts, authorization, node links, offline nodes, federation |
| `admin` | The `sparrow.hub.admin` facet, persistence and reconciliation |
| `web` | `/connect`, tickets, schema and module HTTP resources *(implementation: also the top-level `web.*` annotations, the hub's check of `web.modules`, and a Go client that follows the browser rules of 9.5 and 9.6)* |
| `cmd/sparrow-hub` | The server program |
| `cmd/sparrow-admin` | *(implementation)* A command-line controller: get, validate, commit (and confirm over a new session), confirm, rollback, secrets, watch |
| `examples/echo-node` | *(implementation)* An example node that dials in (`-hub URL -credential C`, with `-hub-pin` for a self-signed hub) or waits to be dialed (`-listen ADDR`, printing its URL and SPKI pin) |

*(implementation)* Reconciliation lives in `hub` (it implements `admin.Applier`); `admin` holds the document, the revision state machine and the stores. The facet-ID table and the last known facets are hub state, kept in the same data directory.

## 2. Configuration

The program reads a small static file at start: listen addresses, TLS certificate and key, the data directory, and the bootstrap administrator (a principal with a credential). Everything else arrives through `sparrow.hub.admin`.

The data directory holds the persisted state of admin section 2.4: the confirmed document and its revision, the revision high-water mark, stored secrets, the facet-ID table and the last known facets of every node. Writes are atomic (write to a temporary file, then rename).

*(implementation)* The static file is JSON: `webtransport` (UDP address, served at `/sparrow/wt`), `websocket` (TCP address, `/sparrow/ws`, TLS unless `websocketPlain`), `tls.cert`/`tls.key` or `selfSigned` with `hosts` (a 10-day certificate whose hash and SPKI pin are logged and written to `-addr-file`; its key is kept in the data directory, so the pin, which nodes dialing in may check, survives restarts), `dataDir`, `bootstrap` (`principal` with `credential` or `credentialFile`, presented as `["bearer", credential]`), optional static `tokens` (token, principal, groups), `web` (`true`, or an object: `audience`, `ticketKeyFile`, `ticketLifetimeMs`, `sessionLifetimeMs`, `modulesDir`, `rootKeys`, `minHostApi`; section 5), `connectTimeoutMs` (section 3), `allowedOrigins`, `shutdownGraceMs` and `log`. Unknown keys are refused. SIGINT or SIGTERM sends `GoAway(going_away)` to every session and node, waits for them up to the grace period and exits.

*(implementation)* Files of the data directory: `state.cbor` (`[revision, document]`, the last confirmed document), `highwater` (written before `commit` returns), `pending.cbor` (only a marker `[revision]` while a commit is pending, so a restart rolls it back as the next revision; the pending document itself is never written), `secrets/<name>` (mode 0600), `hub.cbor` (the facet-ID counter, the table (node, name, major) → ID, the last definition of every ID and the IDs each node last published) and, with `selfSigned`, `selfsigned.key` (PEM). Each file is written to a temporary file in the same directory, synced, renamed over the old one and the directory synced; temporary files a crash left behind are removed at start.

## 3. Nodes

The hub never starts, installs or supervises nodes (Hub Profile, section 10.10). Whatever runs a node, such as an orchestrator, provisions it and registers it through `sparrow.hub.admin`: for a dial-in node, the credential it also hands the node with the hub's URL; for a dialed node, its URL, pin and the credential the hub presents.

- **Dial:** A `Dial` link connects over WebTransport, or WebSocket for `wss` URLs, verifies the pinned key hash and presents `["link", credential]`.
  *(implementation)* Only the pin is checked, not the certificate chain. The credential is sent as a text string when the secret is valid UTF-8, else as bytes. The hub always sends a client schema in `Hello` (possibly empty), so it can update it later. The hub dials when the node is configured or enabled, or the hub starts; an attempt gives up after 10 s. After a failed attempt or the end of a session it dials again with backoff, as a client reconnects: from about 500 ms, doubling up to 30 s, with jitter, reset after a session that got through. A call waiting for the node (below) makes the hub dial at once and then at least every 250 ms while it waits.
- **Dial-in:** nodes with a credential link connect to the hub's listener and present `["link", credential]`.
  *(implementation)* The credential (text or bytes) is compared with the value of each dial-in node's secret. Only a node configured to dial in has a dial-in credential: any other credential, including one of a node the hub now dials or of a disabled node, is refused with `GoAway(unauthenticated)`.
- **Offline:** calls to a node that is not connected wait up to the connect timeout (10 s by default) for it to come back, then fail with `Error(unavailable)`; calls waiting for a node that is removed or disabled fail with `Error(unimplemented)`; a dialed node is redialed with backoff, and at once when a call starts waiting for it.
  *(implementation)* The connect timeout is `connectTimeoutMs` in the static file (`hub.Options.ConnectTimeout`); a call's own deadline shortens the wait, and a deadline that passes meanwhile fails the call with `deadline_exceeded`. Calls waiting for a node that is removed or disabled fail at once with `unimplemented`. Notifications to a node that is not connected are dropped. Only facets a node has published are listed: none before it is first seen; removing a node discards them and retires their IDs; a disabled node's are hidden.
- *(implementation)* **New sessions and changes:** every new node session, dialed or dial-in, is compared with the listed facets and relayed to the other sessions before it takes calls; refused facets close it and keep any old session. A node that is removed or disabled, or whose link or `peer` setting changes, has its session ended at once (no grace period): its running calls end with `Error(unavailable)` toward their callers, then `GoAway(unauthenticated)` and the transport closes; while still configured and enabled it is dialed anew or waited for. At a node's `maxConcurrentCalls` the hub refuses further calls with `resource_exhausted` (`session.CallOptions.NoWait`).
- *(implementation)* **Peers** (`peer: true`) use the same two link kinds; their facets are listed as `<peer-id>/<name>` and a peer exporting a name with `/` is refused (`invalid_argument`).
- *(implementation)* **Provisioning:** `examples/echo-node` shows both sides of it. `-hub URL -credential C` dials in and reconnects with backoff (about 500 ms up to 30 s); `-hub-pin` checks a self-signed hub's SPKI pin. `-listen ADDR` (WebTransport) or `-listen-wss ADDR` (WebSocket over TLS) wait for a hub presenting `-credential` and print `{"webtransport": URL, "websocket": URL, "pin": HEX}`, the values for a `Dial` link; `-key-file` keeps the key, so the pin survives restarts. On SIGTERM it sends `GoAway` and waits for its transport to close.

## 4. Authorization

The built-in policy reads grants from the document's `extensions` under the key `ref.policy`: a CBOR list of `[principal, facet name, level]` with levels `view`, `use` and `manage`. `visible` needs `view`; `allowed` needs `use`, or `manage` for methods annotated `"sparrow.level": "manage"`. A principal's groups are taken from its credential. The bootstrap administrator is always allowed on `sparrow.hub.admin`.

*(implementation)* A grant's principal may also be `*` (everyone) or a group (`group:<id>`, matched against the groups of the credential; static tokens list them). Its facet name is the listed name (`<peer-id>/<name>` for imports), `*` for every facet, or `prefix.*` for every facet whose name starts with `prefix.`. The highest matching level counts. Facet 1 `sparrow.web` is visible to and callable by everyone. Each acting principal of a call is checked on its own: a node's grants, a peer's `node:<peer-id>` grants and `peer:<peer-id>/<principal>` grants are separate entries. The policy is pluggable (`hub.Options.Policy`); with a custom policy `ref.policy` is not accepted. Grants change with the document, and every session whose view changed gets a schema update, while calls no longer allowed end with `Error(permission_denied)` and `Cancel(permission_denied)`.

*(implementation)* Further hub-specific extensions: the document extension `ref.interfaces` (a CBOR list of encoded interface documents) adds interfaces the hub verifies `implements` claims against; `sparrow.hub.admin` is built in. A claim naming an interface the hub holds no document for is refused with `schema_mismatch`, like an incompatible update (10.3). With the Web Profile on, the document extension `ref.web` holds the top-level `web.*` annotations (section 5). Every other extension key, of the document or of a node, is a validation problem.

## 4a. Hub behaviour *(implementation)*

- **Facet IDs:** `sparrow.hub.admin` takes the first free ID of a fresh hub (16), `sparrow.web` is facet 1; node facets get the next free IDs. A removed node's IDs are retired; a disabled node keeps them and is hidden.
- **Compatibility:** the hub keeps the last definition of every facet ID and checks every new version of a node's facet against it, at connection and in updates, also across sessions and restarts.
- **Relayed updates:** each downstream session gets 5 s to ack a node's update, or the change a superseding session brings, and 2 s for an update from a peer hub (`hub.Options.RelayAckTimeout`, `PeerRelayAckTimeout`); the hub acks the node when all have acked or been closed with `GoAway(schema_mismatch)`. The node library gives its hub at least 10 s.
- **Forwarding:** the forwarded `credit` is the caller's (its key, or the default of its stream); `deadline` is lowered by the time spent, including any wait for the node; `context` is 16 random bytes and `principal` the principal the call acts for. When a context's 2 s grace period ends, calls still carrying it are ended: `Error(permission_denied)` to the node, `Cancel(permission_denied)` for the forwarded call. A call forwarded to a peer hub carries no `context` (the peer refuses one, 10.8) and a call acting for a `peer:` principal is never forwarded to another peer.
- **Calls** (7.1, 7.5, 7.6, 10.5; package `session`): a callee stops counting and forgets a call at its own final message, ignoring later input and granting no more credit; on a leased stream it keeps one flag until the caller's `End` or `Cancel`. A caller counts a call until it has sent its last message and seen the callee's final one, and a call on a stream it reset as long as the stream counts. When the node's final message arrives, the hub forwards it and the session sends `End` to the node for a caller whose half is still open.
- **Watch:** after the `Snapshot`, the hub sends the current `NodeEvent` of every configured node, then events as they happen, each with the revision applied when it is sent; after every applied revision each configured node's state is reported again. A removed node is reported once (`removed`), a disabled one `disabled` until it is enabled, and an `offline` message is the last connection failure (a dial error, a pin mismatch, refused facets, or why the session ended). A commit is a no-op only when the canonical encodings are equal byte for byte. A watcher more than 256 events behind is ended with `Error(resource_exhausted)`.
- **Problem paths** use the field names of hub-admin section 3 and the Link variant name down to the field at fault (for example `["nodes", "acme.notes", "link", "dial", "pin"]` or `["nodes", "acme", "link", "credential"]`); keys of the `defaults` map (bytes) appear as lowercase hex. The JSON form (`sparrow-admin`) uses the same names, writes a union as an object keyed by its variant (`{"link": {"dial": {"url": ..., "pin": "<hex>", "credential": ...}}}` or `{"link": {"credential": ...}}`) and byte strings as hex, and refuses unknown keys.
- **Session expiry** (5.5): a client whose credential carries a login session and an end (a Web Profile ticket's `sid` and `sexp`) gets `AuthStatus` 60 s before the end and `GoAway(unauthenticated)` at the end; `AuthRefresh` with a credential for the same principal and login session extends it, anything else ends the session with `GoAway(unauthenticated)`. `Hub.EndLoginSession(sid)` closes a logged-out login session's sessions (9.2).

## 5. Web Profile

The hub serves `POST /sparrow/connect` (tickets are EdDSA-signed JWTs bound to the hub instance), `GET /sparrow/schema/{hash}` and `GET /sparrow/mods/{hash}.{ext}`. How users log in before `/connect` is pluggable; the reference implementation ships a static-token authenticator for development and tests.

*(implementation)* Package `web`, mounted on both listeners when the static file sets `web`:

- **Login:** `web.Authenticator` is the host's HTTP authentication; the program uses `web.StaticTokens` (the static `tokens`, `Authorization: Bearer`, a login session derived from the token lasting `sessionLifetimeMs`, default 8 h). `/connect` needs `Content-Type: application/json`; a login the authenticator marks as cookie-based also needs an allowed `Origin`; a request from another allowed origin gets CORS headers (`allowedOrigins`).
- **Tickets:** JWTs with header `{"alg": "EdDSA", "typ": "JWT", "kid": ...}` and the claims `sub` (the principal), `sid`, `aud`, `exp`, `iat`, `jti`, `sexp`, plus `groups` when the login has groups, so the edge authorizes without asking the host. `aud` is the edge instance (`web.audience`, default the WebTransport endpoint URL); `exp` is `ticketLifetimeMs` after issue (default 45 s, at most 60 s); a ticket whose `exp` is more than 60 s after `iat` is refused. The signing key comes from `ticketKeyFile` (a hex Ed25519 seed) or is made at start. Tickets are presented as `["bearer", ticket]` in `Hello` and `AuthRefresh` and used once: the `jti` is recorded until `exp` (in memory; `web.JTIStore` for edges that share a hostname). The refresh form needs the URL of one of this edge's endpoints and answers `{"ticket": ...}` only.
- **`/connect` answer:** `endpoints` lists WebTransport first, then WebSocket; `serverCertificateHashes` is a list of base64url SHA-256 certificate hashes when the hub runs with `selfSigned`, otherwise `null`; `schemaHash` is the hash of the schema a session of this login gets. An older client `hostApi` than `minHostApi` gets `426`.
- **Schemas** are served only to a principal whose schema has that hash, as `application/cbor`, `private, max-age=31536000, immutable` (schemas vary by permission here).
- **Modules** come from `modulesDir`: any file names, found by the hash of their contents (0x01 ‖ SHA-256); the facets' `web.modules` entries sign them. A file is served only if a facet the requester sees lists it (a module by the extension of its `url`, an asset by the extension of its `path`); it is `public` when the anonymous view (only `*` grants) lists it, and then needs no login, otherwise `private` and needs one. The bytes are checked against the hash before every response; a mismatch is a 500, never the bytes.
- **Annotations:** the document extension `ref.web` is a CBOR map of top-level annotations, each key starting with `web.` (`web.keys`, `web.revoked`, `web.apply` and client configuration); every session's schema carries them. `web.keys` entries need a namespace ending with a dot and `web.apply` is `hot`, `reload` or `prompt`; with `rootKeys` given, certificates and the revocation list must be signed by a root key. A node facet whose `web.modules` is malformed or ships a module outside its scope is refused with `GoAway(invalid_argument)`; signatures, rollback and revocation are the client's to check.
- **`moduleRejected`** (`[id, version, reason]`) is logged, counted and passed to `hub.Options.OnModuleRejected`; a malformed one is dropped.
- **Client:** `web.Client` (`Connect`, `Refresh`, `Schema`, `File`, each checking hashes), `web.Loader` (signatures with `websign`, `hostApi` ranges, rollback records, the revocation list with the highest seq kept, an `AllowUnsigned` development switch) and `web.Snapshot` / `web.Snapshots` (the 9.6 snapshot as a canonical CBOR map, verified before it boots, with the one previous snapshot kept for rollback).

## 6. Testing

*(implementation)* Everything below exists; node processes are `examples/echo-node`, run as separate programs (`internal/testutil.Proc`) that dial in or are dialed, never started by the hub; the browser test (`e2e/browser`, `SPARROW_BROWSER=1`) runs a minimal page in headless Chromium over WebTransport and WebSocket; the hub decodes only with `wire`, `schema` and `admin`, whose decoders are fuzzed (`admin.FuzzDecode` covers the document types). See `go/README.md`.

- Unit tests in every package, and conformance tests against the published test vectors.
- Behaviour scenarios: scripted message sequences with expected outcomes, run against the real server over each binding.
- Integration tests with dialed and dial-in nodes running as separate processes, and two federated hubs.
- Fuzzing of every decoder.
