## File format

Each file is a JSON object:

```json
{
  "spec_revision": "core rev302 (draft); hub-admin rev16 (draft)",
  "generator": "tools/vectorgen-go",
  "area": "calls",
  "vectors": [ { "name": "...", "description": "...", "spec": "7.2", "type": "message", ... } ]
}
```

Every vector has `name` (unique across all files; other vectors refer to it), `description`, `spec`
(section reference) and `type`. All binary values are **lowercase hex** without separators.

### Readable values ("typed JSON")

| CBOR | Typed JSON |
| --- | --- |
| null, true, false, text string | JSON `null`, `true`, `false`, string |
| integer, \|n\| ≤ 2^53−1 | JSON number (always an integer) |
| integer outside that range | `{"$int": "18446744073709551615"}` |
| float (any width) | `{"$float": "1.5"}`; also `"NaN"`, `"Infinity"`, `"-Infinity"`, `"-0"` |
| byte string | `{"$bytes": "00ff"}` |
| tag | `{"$tag": 1, "value": 1795737600}` |
| array | JSON array |
| map with only text keys | JSON object (member order has no meaning) |
| any other map | `{"$map": [[key, value], ...]}` in canonical key order |

A float always appears as `$float`, even when integral, and its wire width is always the shortest
exact width. Floats appear only in message values: canonical data has none (section 3.2). `diag`
fields give RFC 8949 diagnostic notation, where `_1`, `_2` and `_3` mark float widths.

### Encoding used

Every CBOR item here is encoded with **Core Deterministic Encoding** (RFC 8949, section 4.2.1). For
schemas, facets, interfaces and signed data this is required and the bytes are the only valid ones.
Ordinary messages need not sort map keys (3.2), so message bytes are *one* valid encoding. A decoder
must also accept other key orders.

## Test-only keys

All keys in `signing.json` come from trivial seeds (32 × `0x01` … 32 × `0x08`) and are labelled
`TEST-ONLY`. Never trust them in a real client build.

## Spec decisions the vectors rely on

Every question raised while writing these vectors is settled in the spec; the log is in
[`SPEC-ISSUES.md`](../SPEC-ISSUES.md), with the vectors that cover each decision. Points an
implementer is most likely to trip over:

1. A schema **as sent** lists its facets sorted by ID. A received schema with facets out of order is
   invalid (`schema/sent-facets-out-of-order`). The `input` of the other `schema` vectors is a
   valid sent document: its facets are in order, while the contents of each facet are unsorted to
   exercise the canonical form.
2. Facet 1 `sparrow.web` must match its definition by name and facet hash (`facet/sparrow-web`,
   `schema/invalid-facet1-renamed`).
3. Wire shapes clear names, annotations and the hint flags (method 0x1, 0x4; field 0x2). A service is
   compared without its method list, then each interface method on its own. An interface contains
   exactly what its services reach, and references inside tombstones reach nothing.
4. Facet names, node IDs and module ids follow `[a-z0-9-]+(\.[a-z0-9-]+)*` (an imported facet name may
   carry a `<peer-id>/` prefix). Names of types, services, methods, fields, variants and sigils are
   ASCII. TypeIds 12–31 are reserved; a schema that uses one is invalid.
5. A notification (method flag 0x2) has output `unit` and no `[4]` in its input.
6. Making a required field optional is incompatible, and so is changing the type of a field or variant
   when it becomes a tombstone (or afterwards).
7. The nesting limit counts arrays, maps and tags only: 64 nested arrays holding a uint are 64 levels.
8. Forwarded notifications carry no `context`; the hub still sets `principal` (10.5).
9. The admin interface's `errors` lists are empty (all its errors are core status codes), the
   interface carries no annotations, and optional fields are flagged 0x1 and typed `[2, T]`.

Error and reason codes such as `facets_not_sorted`, `facet1_mismatch`, `invalid_notification` and
`invalid_name` are a vocabulary for these files only. The `message` text of `unimplemented/*` errors
still says "part": the bytes of existing vectors were kept unchanged by the rename to "facet".
