## File format

Each file is a JSON object:

```json
{
  "spec_revision": "core rev164 (draft)",
  "generator": "tools/vectorgen-go",
  "area": "calls",
  "vectors": [ { "name": "...", "description": "...", "spec": "7.2", "type": "message", ... } ]
}
```

Every vector has `name` (unique across all files; other vectors refer to it), `description`, `spec`
(section reference) and `type`. All binary values are **lowercase hex** without separators.

### Readable values ("typed JSON")

| CBOR | Typed JSON |
| --- | --- |
| null, true, false, text string | JSON `null`, `true`, `false`, string |
| integer, \|n\| ≤ 2^53−1 | JSON number (always an integer) |
| integer outside that range | `{"$int": "18446744073709551615"}` |
| float (any width) | `{"$float": "1.5"}`; also `"NaN"`, `"Infinity"`, `"-Infinity"`, `"-0"` |
| byte string | `{"$bytes": "00ff"}` |
| tag | `{"$tag": 1, "value": 1795737600}` |
| array | JSON array |
| map with only text keys | JSON object (member order has no meaning) |
| any other map | `{"$map": [[key, value], ...]}` in canonical key order |

A float always appears as `$float`, even when integral, and its wire width is always the shortest
exact width. Floats appear only in message values: canonical data has none (section 3.2). `diag`
fields give RFC 8949 diagnostic notation, where `_1`, `_2` and `_3` mark float widths.

### Encoding used

Every CBOR item here is encoded with **Core Deterministic Encoding** (RFC 8949, section 4.2.1). For
schemas, parts, interfaces and signed data this is required and the bytes are the only valid ones.
Ordinary messages need not sort map keys (3.2), so message bytes are *one* valid encoding. A decoder
must also accept other key orders.

only, not part of the protocol.

## Test-only keys

All keys in `signing.json` come from trivial seeds (32 × `0x01` … 32 × `0x09`) and are labelled
`TEST-ONLY`. Never trust them in a real client build.

## Assumptions

Where rev164 leaves a detail open, the vectors make the choice below. Each is also in
[`SPEC-ISSUES.md`](../SPEC-ISSUES.md) (numbers refer to its section A unless marked C).

1. `implements` has nothing to sort; the canonical schema sorts `parts` by ID (A1, A2).
2. Part 1 `sparrow.web` has version `"1.0.0"`. Part IDs 0 and 2–15 are invalid. Part 1 is checked by
   name only (A3, A4).
3. Compatibility of a replacing part (A5):
   - new struct fields must be optional;
   - enum values can't be removed;
   - member tags stay as tombstones and are never revived;
   - required fields can't be removed;
   - kind, sparse flag, alias target, member types and sigil kinds are fixed;
   - the old `retired` must be kept;
   - methods are matched by MethodId.
4. An in-place replace across major versions is invalid (A6). A removed part ID comes back only with
   the same name and major version, compatibly (A7).
5. References inside tombstones are not resolved (A8).
6. Conformance compares whole services, including method lists and all flags (A9, A10).
7. A float anywhere in a schema makes it invalid (A11).
8. A module id must be the part name plus a dot plus more; equal to the name is rejected. The hub
   prefix is stripped from the part name up to the first `/` and never appears in module ids
   (A12, A13).
9. Namespace coverage is a plain UTF-8 byte prefix, without normalization (A14).
10. A root key listed in a revocation list is ignored; the rest of the list counts (A15).
    `web.keys` and `web.revoked` are top-level annotations (A16).
11. Forwarded payloads are the `input`/`output`/`value`/`details` elements. The hub adds no `credit`
    key the caller didn't send. Principal letters are ASCII (A18–A20).
12. Codes 23–31 map to WebSocket 4023–4031 (A23).
13. Module acceptance order and the `sig` key_id are as in SPEC-ISSUES C1, C2. Hub call IDs on a
    pipe are odd (C3). The forwarding vector assumes 50 ms elapsed (C4).
