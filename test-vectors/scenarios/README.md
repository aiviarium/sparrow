# Behaviour scenarios

Scripted message sequences between a client and a server, with the outcomes the spec requires. Each
`*.json` file here is one scenario, generated by [`tools/vectorgen-go`](../../tools/vectorgen-go)
(`scenarios.go`). **Do not edit them by hand.**

What is checked where:

- **Here (now):** the JS verifier (`tools/verify-js`) and the Go conformance test
  (`go/conformance/scenario_test.go`) check that every message encodes and decodes exactly as stated,
  and that the script is consistent: call-ID parity, stream headers, the credit arithmetic, schema
  epochs and hashes, and that every Request names a method of the scenario schema or is answered with
  `Error(unimplemented)` (or, for a notification, is dropped).
- **Later:** the behaviour itself (who sends what, when, and what must not happen) is executed by the
  session tests of the Go reference implementation (`go/session`), which drive a real session over each
  binding with these scripts. Until those tests exist, the outcomes below are a specification, not a
  passing test.

## The scenario server

Every scenario uses the schema of vector `schema/scenario-host` in `schema.json`: one facet, 16
`test.echo`, with service 0 `Echo`. Each method's behaviour is written in its `doc` annotation:

| Method | ID | Shape | Behaviour |
| --- | --- | --- | --- |
| `echo` | 0 | string → string, idempotent | Returns its input. |
| `count` | 1 | uint → `[3, uint]` (0x10) | Streams the Items 1, 2, …, n, then `End`. |
| `sum` | 2 | `[3, uint]` → uint (0x8) | Returns the sum of the Items; fails at once with `Error(out_of_range)` on an Item above 1000. |
| `upload` | 3 | `Upload` {name, data `[4]`} → uint (0x8) | Returns the number of bytes received for the data token. |
| `log` | 4 | string → unit, notification (0x2) | Records the text; no reply. |
| `events` | 5 | unit → `[3, dynamic]` (0x4, 0x10) | Subscription of dynamic values until cancelled or drained. |
| `note` | 6 | string → `Note` | Added in epoch 1 (`schema/scenario-delta-1`, test.echo 1.1.0, with type 65 `Note`). |

## File format

```json
{
  "format": 1,
  "spec_revision": "core rev324 (draft); hub-admin rev25 (draft)",
  "generator": "tools/vectorgen-go",
  "name": "server-stream-credit",
  "description": "...",
  "spec": "7.2, 7.3, 7.4",
  "given": { "schema": "schema/scenario-host", "session": "established as in ...", "initial_credit": { "2/server": 10 } },
  "steps": [ { "step": 1, "from": "client", "stream": "lease:1", ... }, { "step": 5, "expect": "held_back", ... } ]
}
```

### `given`

| Key | Meaning |
| --- | --- |
| `schema` | The server's schema at the start: the name of a `schema` vector. |
| `session` | `"none"` (the scenario starts at the transport and includes the handshake), or `"established as in scenario handshake-normal (steps 1-3), with no call open"`: the shared lane is open, `Ready` has been received, and both peers use default `params` unless `server_params` / `client_params` say otherwise. |
| `client_cache` | For handshake scenarios: the schema hash and limits the client has cached, or `null`. |
| `server_params`, `client_params` | Params (section 5.4) sent in `Welcome` / `Hello`, as typed JSON. |
| `initial_credit` | Credit each call direction starts with, keyed `"<call_id>/<sender>"`: `"2/server"` is the credit for what the server sends on call 2 (the callee's half). Used with the `counted_bytes` / `credit_after` fields of the steps. |
| `delta` | For schema-update scenarios: the `delta` vector the server's `SchemaUpdate` carries. |

### Message steps

| Field | Meaning |
| --- | --- |
| `step` | 1, 2, 3, … in order. |
| `from` | `"client"` or `"server"`: who writes the message. |
| `stream` | `"shared"` for the shared lane, or `"lease:<n>"` for the n-th leased stream the client opened in this scenario. |
| `opens_stream`, `header` | Present on the first message the opener writes on a stream: it writes the stream header byte (`"00"` shared lane, `"01"` leased stream) before the length-prefixed message (section 4.1). The other direction has no header. |
| `kind_name`, `message`, `diag`, `cbor` | The message as typed JSON (see `../README.md`), RFC 8949 diagnostic notation (informative) and its exact CBOR, without length prefix. |
| `compare` | `"status"`: a runner compares only the kind, call ID and status of the message it receives (the `message` / `reason` text is the implementation's). Otherwise the received message must equal `cbor` after decoding (map key order is free, section 3.2). |
| `counted_bytes`, `credit_after` | The bytes the message counts against its call direction's credit (section 7.4) and the sender's remaining credit after it. On a `Credit` message, `credit_after` is the receiver-side remaining credit of the direction it grants. |
| `violation`, `credit_before` | `true` when the message is sent with no credit left: a credit violation. |
| `crossed` | `true` when the message was already in flight when the previous message from the other peer arrived (it "crosses" it). A runner sends it before reading that message. |
| `note` | Explanation. |

Bindings: on WebTransport each `lease:<n>` is a WebTransport bidirectional stream. On the WebSocket and
pipe bindings there is only a shared lane: a runner sends `lease:<n>` messages on the shared lane
without a header, and `stream_idle` / `streams_open` expectations do not apply. The credit scenarios set
`sharedCredit` and `leaseCredit` alike where it matters, so their numbers hold on every binding.

### Expectation steps

A step with `expect` instead of `from` states what must be true at that point. Implementations check
it; the vector checkers only check that the name is one of these:

| `expect` | Fields | Meaning |
| --- | --- | --- |
| `session_ready` | | The handshake is complete; the server dispatches calls from now on. |
| `dispatched` | `call_id` | The callee runs the call. |
| `not_dispatched` | `call_id` | The callee never runs the call (its handler is not invoked). |
| `call_ended` | `call_id` | Both halves are finished; both peers forget the call ID (7.1). |
| `half_finished` | `call_id`, `half` | The `"caller"` or `"callee"` half of the call is finished. |
| `stream_idle` | `stream` | The leased stream carries no call and is back in the client's pool (4.2). |
| `streams_open` | `by`, `count` | How many leased streams that peer has open. |
| `held_back` | `by`, `call_id`, `reason`, optional `epoch` | That peer sends nothing more for the call until the reason goes away: `"credit"` (no credit left, 7.4) or `"schema_ack"` (the message would use an ID of an unacknowledged epoch, 6.6 rule 1). |
| `no_reply` | `call_id` | The callee sends nothing for this call (a notification). |
| `discarded` | `by`, `call_id` | That peer reads and drops the messages just received for the call. |
| `violation` | `by`, `call_id` | The named peer broke the credit rule for the call. |
| `session_closed` | `by` | That peer sends its last message and closes the session. |
| `transport_closed` | `by` | That peer closes the transport after the drain. |
| `client_retries` | `call_id` | The client resends the call on a new session. |

## Scenarios

| File | What it shows | Spec |
| --- | --- | --- |
| `handshake-normal.json` | Hello, Welcome with the full schema, Ready, one unary call on a new lease | 4.1, 5.2, 5.4 |
| `handshake-optimistic-match.json` | Optimistic start with a current cache: the early call runs | 5.3 |
| `handshake-optimistic-mismatch.json` | Optimistic start with a stale cache: Welcome, `GoAway(schema_mismatch)`, no call runs | 5.3 |
| `unary-lease-reuse.json` | Two unary calls reuse one leased stream | 4.2, 7.1 |
| `server-stream-credit.json` | Credit runs out, the server holds back, a `Credit` grant resumes it; `End` is never held back | 7.4 |
| `client-stream-cancel.json` | `Cancel` → `Error(cancelled)` → call ended, stream idle and reusable | 7.1, 7.5 |
| `upload-referenced-token.json` | Byte upload by reference: token 1, two chunks, `End` | 7.8 |
| `callee-error-while-streaming.json` | The callee errors while input still arrives; crossed Item discarded; caller sends `End` next | 7.1 |
| `credit-violation.json` | The caller sends data with no credit left: `Error(protocol_error)`, then `End` | 7.4 |
| `schema-update-ack-gating.json` | Messages using IDs of epoch 1 wait for `SchemaAck(1)` | 6.6 |
| `goaway-drain.json` | `GoAway(going_away)`: a crossing Request gets `Error(going_away)`, running calls finish | 5.6 |
| `notification-shared-lane.json` | A notification on the shared lane gets no reply | 7.1, 7.3 |
| `notification-unknown-dropped.json` | Notifications to an unknown facet or method are dropped; the session goes on | 7.1 |
| `unknown-facet-or-method.json` | `Error(unimplemented)` for an unknown facet and an unknown method | 7.1 |
